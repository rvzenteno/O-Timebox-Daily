# Timebox v1.6 Phase 1 Technical Design: Task Sheet Discovery & Saved Views

**Date**: 2026-09-16  
**Document Status**: Pre-Implementation Design Specification  
**Target Milestone**: Timebox v1.6 — Phase 1  
**Scope**: In-Memory Search, Multi-Filter Engine, Grouping Engine, and Plugin-Persisted Saved Views  

---

## 1. Architectural Overview & Boundary Isolation

Phase 1 enhances the interactive **Task Sheet View** into an ergonomic discovery interface for complex, multi-tiered projects. 

### Core Architectural Rule: Zero Markdown Footprint
Phase 1 introduces **zero new persistent fields** to project Markdown files or YAML frontmatter. All search, filtering, grouping, and Saved View preferences operate exclusively as **in-memory view projections** over the normalized project model (`NormalizedProject`).

```mermaid
graph TD
    subgraph Canonical Project Model (Untouched)
        A[Markdown File / Frontmatter] --> B[NormalizedProject]
        B --> C[Four-State Engine: Baseline, Plan, Actuals, Forecast]
    end

    subgraph Phase 1 View Pipeline (In-Memory)
        C --> D[Active Task Sheet Rows]
        D --> E[Filter Engine: Search, Chips, Dropdowns]
        E --> F[Grouping Engine: WBS, Resource, Status]
        F --> G[Rendered DOM Table & Counter]
    end

    subgraph Preference Layer (Isolated)
        H[Obsidian Plugin Settings: taskSheetPreferences] -.-> E
        H -.-> F
        H -.-> I[Saved Views Definitions]
    end
```

The four-state execution lifecycle:
$$\text{Baseline} \longrightarrow \text{Current Planned Schedule} \longrightarrow \text{Actual Execution} \longrightarrow \text{Forecast}$$
remains strictly frozen and unaffected by view-level filters or grouping.

## 2. In-Memory Search & Filtering Specification

### 2.1 Search Query Engine
- **Target Fields**: Case-insensitive substring matching against:
  - Task Title (`task.title`)
  - WBS Code (`task.wbsCode`)
  - Assigned Resource Names and IDs (`task.assignments`)
  - Task Tags (`task.tags`)
  - Task Priority (`task.priority`)
  - Notes & Prose Descriptions
- **Debounce**: 150ms input debouncing to prevent frame drops during rapid typing on 1,000+ task projects.
- **Shortcut**: `Ctrl+F` / `Cmd+F` inside Task Sheet focuses the search input. `Esc` clears the search query.

### 2.2 Multi-Criteria Filter Architecture
The filter engine evaluates each task against a composite filter state object:

```typescript
export interface TaskSheetFilterState {
    searchQuery: string;              // Text substring match
    quickFilter: QuickFilterId;       // 'all' | 'critical' | 'slipped' | 'assigned-me' | 'unassigned' | 'milestones'
    statusFilter: TaskStatusFilter;   // 'all' | 'not-started' | 'in-progress' | 'completed'
    resourceFilter: string;           // 'all' | resourceId
    priorityFilter: string;           // 'all' | 'high' | 'normal' | 'low'
}

export type QuickFilterId = 
    | 'all' 
    | 'critical' 
    | 'slipped' 
    | 'assigned-me' 
    | 'unassigned' 
    | 'milestones';

export type TaskStatusFilter = 
    | 'all' 
    | 'not-started' 
    | 'in-progress' 
    | 'completed';
```

### 2.3 Filter Evaluation Rules

| Filter Identifier | Evaluation Predicate | Description |
|:---|:---|:---|
| **Critical Path (`critical`)** | `task.totalFloat <= 0 && !task.isSummary` | Surfaces driving path tasks with zero float. |
| **Slipped Tasks (`slipped`)** | `(task.variance?.finishVariance > 0) || (task.forecastFinish > task.calculatedFinish)` | Tasks running late relative to active baseline or current plan. |
| **Assigned to Me (`assigned-me`)** | `task.assignments.some(a => a.resourceId === currentUserId)` | Matches current user's designated resource ID in plugin settings. |
| **Unassigned (`unassigned`)** | `task.assignments.length === 0 && !task.isSummary` | Orphaned work packages lacking staffing. |
| **Milestones (`milestones`)** | `task.isMilestone === true || task.durationDays === 0` | Zero-duration decision checkpoints. |
| **Status: Not Started** | `task.percentComplete === 0 && !task.actualStart` | Tasks not yet mobilized. |
| **Status: In Progress** | `(task.percentComplete > 0 && task.percentComplete < 100) || (task.actualStart && !task.actualFinish)` | Active tasks underway. |
| **Status: Completed** | `task.percentComplete === 100 || task.actualFinish !== undefined` | Finished historical tasks. |
| **Resource Filter** | `task.assignments.some(a => a.resourceId === selectedResId)` | Isolates individual contractor/engineer workload. |

### 2.4 Hierarchical Summary Task Display Rule
When filtering is active:
- A summary task is visible if **any of its descendants match the filter**, or if the summary task itself matches.
- Matching leaf tasks always display their parent outline chain in muted styling to preserve structural WBS context.

## 3. Grouping Engine Architecture

By default, the Task Sheet displays tasks in standard hierarchical WBS order (`1`, `1.1`, `1.1.1`). Phase 1 introduces a dynamic grouping transform that organizes task rows without altering the underlying project data:

```typescript
export type TaskGroupingMode = 'wbs' | 'resource' | 'status';
```

### 3.1 Grouping Modes

#### 1. Group by WBS (Default)
- Standard outline hierarchy based on `task.wbsCode` and Markdown indentation depth.
- Parent rows display recursive rollups (dates, duration, work, cost, progress) and expand/collapse chevrons.

#### 2. Group by Resource
- Tasks are grouped under resource header bars corresponding to `project.resources`.
- Tasks with multiple assignments appear under each assigned resource header.
- Tasks lacking assignments appear under a distinct `⚠️ Unassigned Tasks` section header.
- Resource header displays total assigned tasks, total work hours, and over-allocation warning icon if peak utilization exceeds 100%.

#### 3. Group by Status
- Tasks are categorized into 3 standardized execution sections:
  1. `📋 Not Started` ($0\%$ complete)
  2. `⏳ In Progress` ($1\% - 99\%$ complete)
  3. `✅ Completed` ($100\%$ complete)
- Each status header displays task count, rolled-up work hours, and average completion.

The Task Sheet toolbar is enhanced with a dedicated discovery deck positioned immediately above the table header:

```
+---------------------------------------------------------------------------------------------------------------+
| [+ Task]  [+ Subtask]  [👁️ Columns]  [🔍 Search tasks (Cmd+F)...              ]  [Clear Filters]              |

+---------------------------------------------------------------------------------------------------------------+
| WBS  | Title                            | Dur | Start      | Finish     | %   | Predecessors | Assigned       |
| 1.1  | Architectural Specs              | 7d  | 2026-09-14 | 2026-09-22 | 100 |              | @alice-eng     |
| 2.2  | Excavation & Utility Trenching   | 8d  | 2026-09-30 | 2026-10-09 | 75  | 2.1FS        | @dave, @bob    |
```

### 4.1 UI Components & Interaction Ergonomics
1. **Search Input**: Clean rounded search field with embedded search icon (`search`) and a 1-click clear button (`x`).
2. **Filter Chips**: Horizontal pill buttons with active state highlighting (`.timebox-filter-chip.is-active`).
3. **Resource Dropdown**: Native select element listing all project resources plus `Unassigned`.
4. **Group Switcher**: Segmented toggle control (`WBS`, `Resource`, `Status`).
5. **Result Counter**: Real-time readout: `Showing X of Y tasks (Z hidden)`. When filters hide tasks, an amber dot appears next to the counter.
6. **Clear Filters Button**: Appears only when an active filter is applied; restores `all` state in one click.

## 5. Saved Views Architecture

To prevent repetitive filter setup, Phase 1 introduces **Saved Views**.

### 5.1 Built-in System Presets
Six standard presets are bundled out-of-the-box:

| Saved View Preset | Filter Configuration | Visible Column Preset | Grouping Mode | Primary Use Case |
|:---|:---|:---|:---:|:---|
| **All Tasks (Default)** | All tasks, no filters | Core Columns | WBS | Standard project planning and review. |
| **My Open Tasks** | Assigned to Me, Incomplete | Core + Remaining Work | Status | Individual daily execution check. |
| **Critical Tasks** | `totalFloat <= 0`, Incomplete | Core + Total Float | WBS | Progress meetings & path mitigation. |
| **Slipped Tasks** | `finishVariance > 0` | Baseline & Variance | WBS | Schedule delay audits. |
| **Milestones** | Milestones only | Core + Predecessors | WBS | Executive checkpoint review. |
| **Tracking & Variance** | All tasks | Baseline & Variance + Execution | WBS | Status date control and reporting. |

### 5.2 Storage Specification: Plugin Settings Only
Saved Views are user interface preferences and must **never enter project Markdown notes**. They are stored in Obsidian's plugin configuration:

```typescript
export interface TimeboxPluginSettings {
    // Existing settings...
    taskSheetPreferences: {
        visibleColumnIds: string[];
        currentUserId: string;              // Maps to @resource-id for "Assigned to Me"
        savedViews: SavedViewDefinition[];  // User-defined and custom views
        activeSavedViewId: string;
    };
}

export interface SavedViewDefinition {
    id: string;
    name: string;
    isSystemPreset: boolean;
    filterState: TaskSheetFilterState;
    visibleColumnIds: string[];
    groupingMode: TaskGroupingMode;
}
```

## 6. Performance Strategy Across Project Scales

All search, filtering, and grouping operations operate strictly on the in-memory `NormalizedProject` cache, bypassing Markdown re-parsing and CPM recalculation.

| Project Scale | Filter / Search Strategy | Expected Latency | Rendering Technique |
|:---|:---|:---:|:---|
| **100 Tasks** | Pure linear array `.filter()` and `.sort()` | $<1\text{ms}$ | Full table DOM replacement via `DocumentFragment`. |
| **500 Tasks** | Linear filter; debounced input (150ms) | $<3\text{ms}$ | DocumentFragment batch DOM replacement. |
| **1,000 Tasks** | Linear filter on cached normalized task array | $<8\text{ms}$ | Cached row elements with CSS visibility toggling (`display: none`). |
| **5,000 Tasks** | Pre-indexed token maps (lower-case title/WBS tokens) | $<25\text{ms}$ | Fragment batching; viewport slicing to prevent layout thrashing. |

### Memory & CPU Guardrails
- **Zero Allocations in Render Loop**: Filter predicates evaluate existing task object references; no object cloning or deep copies are performed.
- **Zero Markdown Mutations**: Changing filters emits zero file write events to Obsidian's vault.

## 7. Automated Test Plan for Phase 1

1. **Unit Tests (`test/taskDiscovery.test.ts`)**:
   - Substring text search across titles, WBS codes, and resources.
   - Critical path filter accuracy ($TF \le 0$).
   - Slipped tasks filter against active baseline ($finishVariance > 0$).
   - Group by Resource transform: verification that multi-assigned tasks appear in multiple buckets and unassigned tasks bucket correctly.
   - Group by Status transform: verification of 0%, 1–99%, and 100% partitioning.
2. **Integration Tests (`test/savedViews.test.ts`)**:
   - Saved View persistence in plugin settings.
   - Switching Saved Views restores column visibility and filter state simultaneously.
   - Preservation of Markdown note content across all filter and view operations.
3. **Scale Benchmark**:
   - 1,000-task search and filter execution completed in $<15\text{ms}$.
